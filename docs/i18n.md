# TactiTwin ES/EN localization contract

TactiTwin is bilingual by design. Spanish (`es`) and English (`en`) are first-class product languages from the beginning of development.

## Architecture rule

Tactical calculations must be language-neutral. IDs, metric keys, risk levels, channel codes, zone codes and numeric scores are canonical machine values and must not change when the output language changes.

User-facing content is localized at the presentation/output layer:

- scenario names
- tactical recommendations
- explanatory warnings
- method notes
- level labels
- channel labels
- zone labels
- WordPress admin UI
- future reports and exports

The runtime localization service is `TactiTwin_I18n`.

## Supported languages

- `en` — English
- `es` — Spanish

Unsupported locale codes fall back to English. WordPress locales such as `es_ES`, `es_MX`, `en_US` and `en_GB` are normalized to their base supported language.

## REST contract

Scenario endpoints accept an optional `lang` parameter:

- `lang=en`
- `lang=es`

Example:

`GET /wp-json/tactitwin/v1/scenarios/full-matchup-scan?team_id=1&opponent_id=2&limit=5&lang=es`

Machine fields remain canonical regardless of language. Localized presentation fields include `scenario_name`, recommendation texts, warning texts, method notes and `level_label`.

## Scenario Lab

Scenario Lab exposes an explicit language selector. This makes report language independent from the WordPress installation language and lets a coach generate the same matchup assessment in Spanish or English without recalculating different tactical logic.

## Development rule for new scenarios

A new scenario is not complete unless:

1. its user-facing strings exist in both ES and EN;
2. tactical codes and numeric scores remain identical in both languages;
3. a regression test verifies localization does not alter calculations;
4. REST and Scenario Lab can render it in both supported languages.

## WordPress gettext

The plugin declares:

- `Text Domain: tactitwin`
- `Domain Path: /languages`

Standard WordPress admin strings should continue using gettext functions (`__`, `_e`, `esc_html__`, etc.). Runtime-generated tactical narratives use `TactiTwin_I18n` so API consumers and generated reports can explicitly select a language.

Release packaging should compile gettext catalogs into `.mo` files for WordPress UI translations while keeping the runtime tactical catalog available for scenario/report output.
